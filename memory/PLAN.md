# Lyra Memory — The Plan

_Consolidated 2026-11-21 (Daniel + Lyra). This is the single document for Lyra's memory: every decision made through 2026-11-21 is folded into the body, not layered on as amendments. Canonical copy: `~/Documents/LyraOS/memory/PLAN.md` on the Fedora._

**Status: PLAN ONLY — nothing is built, and nothing gets built until Daniel says so.** Phase 0 (the inbox) was built 2026-11-15 and removed 2026-11-17 at Daniel's order; the inbox is currently OFF. Every other phase is unbuilt.

## Principles

1. **Authority lives in the runtime, not the weights.** Facts live in files the code owns. The live model reads views; it is never the source of truth for a fact.
2. **Two pens, and Daniel's voice.** Code holds the pen for the *record* (append-only, no interpretation). The curator holds the ONLY pen for *memory* — what becomes durable and what gets fixed is hers alone. Daniel holds no pen, and there is deliberately no memory-editing surface: his corrections happen in conversation and are filed automatically as a note to the curator the moment they land. The notebook is what supersedes: a correction note outranks the stored claim from the moment it is written — in retrieval that evening and in the curator's pass at night — because context gets summarized, and a correction must never depend on surviving a summary. The live model holds no pen either — she takes notes and proposes, never promotes.
3. **Move up, not down.** The curator is a step up from the live model in reasoning. Curation quality is the whole game; a weak curator pollutes the store permanently.
4. **Context is spent where it pays.** Her live window stays lean (the budget principle is why she works). The sleep model gets the big window — curation is where context buys correctness, and it runs unhurried, overnight, as a batch.
5. **Inferences are labeled, never baked in.** Derived conclusions carry their reasoning chain and stay distinguishable from facts, or they are derived on the spot at answer time.

## The record — L0

Everything durable traces back to an append-only record that code writes and nothing interprets:

- **Inbox.** Code appends every turn to a per-day JSONL log (`memory/inbox/YYYY-MM-DD.jsonl`): timestamp, speaker, transcript, tool calls and their results, alarm/device events, and her memory proposals. Immutable once written. No fact exists only as a summary. A "day" is the calendar day (America/New_York), midnight to midnight: at 00:00 the day's inbox and notebook close, the new day's open, and the completed day goes to the sleep pass.
- **Notebook.** The running brain's notes live in a parallel per-day stream (`memory/notes/YYYY-MM-DD.jsonl`) — also code-written, also append-only — so every day has two files: what was said, and what the running brain marked about it. Two kinds of notes: *proposals* (moments she judges worth remembering) and *corrections* (moments Daniel fixes a fact in conversation: what memory said, what he said instead, the quote — filed automatically the moment the correction happens, never an extra step for him). A correction note is an instruction to the curator: the supersession it calls for gets made. **Backup net (Daniel, 2026-11-21):** because filing depends on the running brain noticing in the moment, code also scans the day's inbox log during the pass for correction-shaped moments ("no, it's…", "actually…", "not X — Y") and flags them as candidates. A flag is a pointer, not a note: the curator verifies each candidate against the transcript, and only a verified one is treated as a correction.
- **Raw sources.** Material Daniel hands her through a dashboard upload spot (a mailbox, not an editor): chat exports, documents, anything text-shaped. An upload lands in `memory/sources/` as an immutable original with a manifest line (name, date uploaded, size, hash), and is chunked and embedded on arrival, so a source far bigger than any context window stays workable. A source is a document, not Daniel asserting facts in the room today: in-chat statements and notebook corrections outrank source-derived claims wherever they disagree. **Limits (Daniel, 2026-11-21): text files and PDFs only, 50 MB per file** — generous enough that no real document hits it, tight enough to catch an accidental video or archive drop.

## The store — L1 claims, L2 entities

- **L1 — Claims (durable facts).** The curator extracts discrete claims: subject entity, relation, object, the source quote with a pointer into the record (an inbox line, a notebook entry, or a source passage), date learned, confidence, salience, and an optional validity window (some facts expire). A correction creates a new claim that *supersedes* the old one; the chain is preserved, never edited away. The store is files-first (Daniel, 2026-11-21): markdown and JSONL files are the truth, in the conventions of Muse's own memory stack — curated files, a page per entity, supersede-never-edit — and the SQLite index is a rebuildable cache over the files, never the record.
- **L2 — Entities.** People, places, and things get pages (plain markdown, portable). Facts hang off entities; this is where cross-fact connections live (the two-hop problem: Daniel → works at → Stuart Jones Electric → located in → Jacksonville). Entity resolution — noticing two mentions are the same thing — is an explicit, named job of the curator.
- **Embeddings + vector index.** Claims, entity pages, and source chunks are embedded when written (and a query is embedded at lookup time) by the embedding model served beside the stack — the single-instance rule applies to it like every shared service. The model is NVIDIA's Nemotron-3.5-Embed-1B (Daniel, 2026-11-21), run at BF16 — deliberately not quantized: an embedding is a permanent artifact that every future match depends on, quantization noise would be baked into the index forever, and at ~2.2 GB for the text tower the saving buys nothing. Text tower only — the vision projector is not loaded (embedding document images as sources is a possible future, not this plan). The GGUF is converted from NVIDIA's official BF16 checkpoint with llama.cpp's own converter, keeping the sourcing rule clean. The vectors live with the store (SQLite alongside the claim index; portable, inspectable, no external service). Retrieval is hybrid: vector similarity for meaning, keyword/entity match for exact names, merged before anything reaches her.
- **A graph in shape, not in store (decided, Daniel, 2026-11-21).** Claims are (subject, relation, object) triples tied to stable entity IDs, so the store IS a graph from day one: entities are nodes, claims are edges, and multi-hop questions are answered by walking the claim index (chained lookups) plus the entity pages. No dedicated graph database: at this scale a walk is graph traversal in substance, and a second store would be a copy of the truth that can drift. If walks ever get slow or shallow, a graph store can be generated from the triples later without re-curating a single claim.

## Her view — L3 in-play list, L4 runtime state

- **L3 — The in-play list.** What injection cannot do is surface what the conversation never points at — so the one always-injected layer is not a digest of facts but a list of what is currently *in play*: open threads and pending items. The curator flags claims as open (and closes them when they resolve); the list injected into her prompt is *rendered from those flagged claims* — a view over the store, not a written summary, so there is nothing to drift and no facts are copied into it. Standing facts are NOT on it: they reach her by ambient injection and lookup. (This replaces the original state-card digest, cut by Daniel 2026-11-21: a hand-written prose summary of the claim store duplicates what injection surfaces and can drift from it.) Example shape:

  ```
  IN PLAY
  - DOC recommendation (Alex): sent 2026-11-13, reply pending
  - Probation check-in: early December
  - Jellyfin key: needs recreating
  ```

  Its size is simply the count of open threads — the curator keeps it honest by closing threads, not by squeezing prose into a token budget.
- **L4 — Runtime state.** Commitments (alarm, notes, reminders) stay in code-owned state files, exactly as the alarm does today. Prose memory never becomes load-bearing for an action.

## Working memory and the compaction seal

Three mechanisms cover three timescales, and they must not bleed into each other:

- **Turns (seconds–minutes).** Full session history — the whole session goes to the model, bounded by the 30-minute idle clear and a large token safety valve. On its own it is still amnesia with a hard edge; the edge just sits at the end of a session instead of mid-conversation.
- **Compaction (within one conversation).** If a session grows toward the safety valve, the oldest turns fold into a running session summary instead of vanishing; the live context becomes summary + most recent turns, so a long conversation can run indefinitely. The live model writes the summary at fold time — cheap and immediate, and allowed to be imperfect, because of the seal below. The summary dies at the 30-minute idle clear, exactly like the history does today.
- **In-play list (across days).** Nightly and curated — see L3. It cannot carry intra-day continuity; that is compaction's job.

**Compaction never enters the record (Daniel, 2026-11-15) — this is what makes it safe.** The summary exists only inside the live model's open context window, as a context-management device. It is never written to the inbox: the log contains turns and events only, appended by code from what actually happened, and the curator reads that log — so the curator never sees a summary at all, and there is nothing to label or police. Durable facts are minted in exactly one place: the curator, working from the full raw log. A summary can therefore be wrong without consequence beyond the conversation it serves, and the leak — a live-model summary hardening into a durable "fact" — cannot happen, because the summary never crosses into anything the durable side reads. Corrections are the sharp case, and they are safe by the same construction: a correction never lives only in context — code writes it to the notebook the moment it happens, on the record side of the seal — so no summary can carry it, mangle it, or drop it; the notebook, not the context, is what supersedes.

**Scope: strictly local Lyra (Daniel, 2026-11-21).** This memory is Lyra's alone. The Muse brain path is removed entirely — the dashboard selector has no Muse option and the core is local-only again (removal committed the same night) — and Muse-path turns are not part of this system at all: they are not Lyra's conversations, they are not logged in the record, and they are not curated. Muse is separate, with its own memory; nothing crosses over in either direction.

## Retrieval — how the store reaches her

Memory does not have to *live* in her context to be hers. Three channels:

1. **The in-play list** — always injected (above): the open threads, the one thing topic-driven retrieval cannot surface unprompted.
2. **Ambient injection (pushed, permissive).** She should not have to decide to remember. On each user turn the router embeds the incoming message (with a little of the thread around it) and queries the same index the lookup tool uses; the few claims that clear a relevance bar are placed quietly in her context as things that come to mind — statement and date, nothing more. She may use one, or none: nothing is owed a mention, nothing is announced as a memory, and below the bar nothing is injected at all. This is the channel that lets her say "yeah, she did that last week too" when Daniel mentions the cat — last week's claim surfaced because the topic called it up, not because she thought to run a lookup. Guards: a similarity threshold (silence is the default — the bar's value is calibrated at build time against real claims, since it is a property of the embedding model's score distribution and cannot be picked in advance), a hard cap of 3 claims per turn (Daniel, 2026-11-21), notebook corrections checked first (a corrected claim never surfaces in its stale form), dedupe against the state card and against claims already surfaced this session, and each claim's date rides along so she places things in time honestly instead of inventing the connective tissue.
3. **The lookup tool (pulled).** A `memory_lookup` tool in the router (sibling of `weather_report`): she asks with a question or a subject; it returns claims as tool facts — statement, source quote, date learned, confidence — and she composes the answer. Retrieval checks the notebook first: an unprocessed correction note touching the subject outranks the stored claim, and the tool returns the corrected fact (marked as Daniel's correction, pending curation) rather than the stale claim — the curator formalizes the supersession at night; she does not decide whether it counts. Tool results are the one channel she already handles correctly; a retrieved fact arrives with its evidence attached, never as anonymous prompt text.

## The sleep cycle

- **Window.** Fixed at midnight (Daniel, 2026-11-21): at 00:00 the completed day's logs close, she enters sleep, and the pass takes that day first; when she wakes, the new day's log is already open and collecting. NO finish deadline: the pass runs until the catch-up queue is drained, however long that takes. If she is still asleep come morning, she simply is not usable until it finishes — accepted, for now. The alarm is no part of this trade: it sits outside her, in code-owned clockwork (L4), and fires on schedule whether she is awake, asleep, or mid-curation.
- **Face.** While state = asleep, the TV plays her sleep animation (SLEEP_MOTION, haru_g_m19 — reserved 2026-11-15). The display state machine gains a third state: awake / off / asleep.
- **Spin-down / spin-up.** When she sleeps, the whole voice stack spins down: the live llama-server (9B, awake-hours only, thinking off) stops, and Kokoro, Parakeet, and Whisper stop with it — nothing can hear or speak while she sleeps, which is the same fact as her being unusable. The only model in VRAM overnight is the curator: the Nemotron Nano 12B v2, loaded with thinking on at the highest reasoning tier, at a large context (target 64K) — the emptied card is what gives it the room. The embedding service stays up: the curator embeds through it as she writes. After curation, the curator unloads and the whole stack spins back up. The alarm is untouched by all of this — its tone is code-side paplay on the default sink; only the spoken morning note waits for her to wake, if she is still curating at 06:00.
- **The pass — a day-by-day catch-up.** The curator works a queue, not just last night: starting from the first day not yet completed, she takes that day's inbox log *plus* that day's notebook, and reads them together with the existing claims and entity pages in the same window — this is why the big context matters: superseding a fact requires seeing the old claim and the correction together, and resolving an entity requires seeing both mentions. She applies everything that day calls for — promotions, merges, and every supersession the correction notes instruct — updates the open-thread flags, marks the day complete, and moves to the next day, until every day through today is completed. Only then does she turn to raw sources: pending uploads in upload order, each read and mined for durable claims and marked curated when done — sources never jump ahead of days. A completion cursor (the last completed day) is the pass's only bookkeeping. Each completed day also gets its line in the curation report (what it promoted, merged, superseded, and why) — dated files under `memory/reports/`, surfaced in the dashboard as a read-only view (latest first, history behind it; Daniel, 2026-11-21). It is a window, not an editor: nothing in it leads to a change.
- **Failure safety.** If the pass fails (a crash or an error — there is no deadline to hit), the stack spins back up and she wakes with the latest in-play list; completed days stay completed, and the next run resumes at the first uncompleted day. An overrun is not a failure: the pass simply keeps going into the morning and she is unusable until the queue drains (see Window). The record is append-only, so no day is ever lost — a missed night just means a longer queue the next night.

## The curator

Requirements: a clear step up from the 9B in reasoning; large context; must run on the night-time GPU budget (16 GB VRAM, with system-RAM offload acceptable — it is a batch job, speed is secondary).

- **The curator is the Nemotron Nano 12B v2** (Daniel, 2026-11-21): the 12B version of her own model — her 9B v2 was compressed from it — loaded alone in VRAM for the night shift, thinking enabled at the highest reasoning tier. The other candidate was the same 9B with thinking enabled; the bake-off protocol below remains as the pick's validation on real logs, and the thinking-enabled 9B is the standing fallback if the 12B ever fails it.
- **Bake-off protocol.** Once the inbox has real days in it, run each candidate over the same days of actual conversation logs. Grade: extraction precision (no invented facts), recall of durable facts, entity merges done correctly, corrections superseded correctly, and a planted two-hop connection (Stuart Jones test) found. Winner curates.
- **The pipeline is model-agnostic** (an OpenAI-compatible endpoint plus a context size). On the future Strix Halo box (128 GB unified), the curator becomes a 70B-class model with 128K context with no redesign — the swap is a config change.
- Model sourcing rule stands: official publisher repos (Daniel's Unsloth waiver was for the current 9B; a curator pick gets its own decision).

## Context plan

- **Live (9B):** stays at 8K. Her SOUL (personality and rules — the "brief") + the in-play list + tool results + session history. Injection and lookup are what grow her effective memory without growing the window; the in-play list adds only the open threads. A stretch to 16K is optional later if VRAM measurements allow; it is not required by this design.
- **Sleep (curator):** 64K target on this hardware, 128K on the Halo. Whole day + claim store + entity pages in one view. This is the "don't rush" budget: curation quality is context-bound, so the context goes to the curator.
- This design doc is itself part of the context plan: the reasoning is written down so no future session has to re-derive it under pressure.

## Phases

- **Phase 0 — Turn the inbox back on.** Core-side JSONL logging of turns and events (L0), plus the per-day notebook file. No model change, no behavior change, nothing injected into her prompt. Highest value per effort: every day from switch-on is curatable later, including days before the rest exists. (A first version was built 2026-11-15 and removed 2026-11-17; this phase rebuilds it as designed here.)
- **Phase 1 — Store, retrieval + in-play list.** Claim and entity formats on disk, files-first (markdown + JSONL as the truth, SQLite only as a rebuildable index, portable formats only) with embeddings and a vector index over claims and entity pages; the `memory_lookup` retrieval tool in the router; ambient injection of topic-relevant claims into her context on each user turn; and the core change that injects the in-play list into the router prompt. An empty list and an empty store reproduce today's behavior exactly, so this lands safely before any curator exists.
- **Phase 2 — The sleep job.** Display state machine gains "asleep" (sleep animation wired), the spin-down/spin-up scripts, the curation pass, the curator bake-off on accumulated real logs, and the curation report and its read-only dashboard view.
- **Phase 3 — Her voice in it.** The `memory_note` tool for the running brain (proposals + automatic correction notes); inference labeling in her answers (she can show the hops behind a derived belief). Deliberately NOT in this phase, or any phase: a memory-editing surface for Daniel — no dashboard tile, no strike-a-claim. His control surface is the conversation itself; the curation report is his window, not an editor.
- **Phase 4 — Raw sources.** The dashboard upload spot (a mailbox, not an editor); the `memory/sources/` store with its manifest; chunking + embedding on arrival; and the curator's source pass after the day queue, minting claims and entity material with source provenance.

Explicitly **not** in this plan: the live model curating itself; fine-tuning/LoRA on the logs (separate parked idea); any cloud curation (local-first stands).
